## 1. 设计目标与原则

### 1.1 目标

在一期「工具箱」之上增加两层能力，且不破坏现有侧边栏/管理后台契约：

| 层级 | 能力 | 对顾问的价值 |
| ---- | ---- | ------------ |
| L1 知识库 RAG | 集团客观事实据实回答 | 「知道什么说什么」 |
| L2 综合推理 | 规划 → 调多能力 → 综合建议 | 「想清楚再开口」 |

### 1.2 设计原则（继承一期红线）

1. **重建议、轻代劳**：禁止代发企微消息；发送键在顾问手上。
2. **有出处才说**：RAG 无命中 / 低匹配必须兜底，禁止幻觉。
3. **过程透明**：综合推理每步经 SSE 推送，顾问可打断。
4. **可秒级回退**：全局开关关闭后立即进入简化模式（L1 RAG 和/或一期单模块建议）。
5. **复用一期基建**：鉴权、客户守卫、`suggestion_event` 采纳闭环、`audit_log`、Redis Stream、AI Gateway 模式不变。

## 2. 总体架构

### 2.1 逻辑架构（在一期六层上增量）

```
┌─────────────────────────────────────────────────────────────────────┐
│ ① 接入层     企微侧边栏 H5（步骤流水 + 建议卡）  管理后台（知识库/开关）│
├─────────────────────────────────────────────────────────────────────┤
│ ② 网关层     JWT · 限流 · 审计 · SSE                                           │
├─────────────────────────────────────────────────────────────────────┤
│ ③ 业务服务层（一期模块 + 二期增量）                                              │
│   profile │ reply* │ tag │ schedule │ admin*                                  │
│   ★ knowledge（知识库管理/检索编排）                                           │
│   ★ agent   （综合推理编排 / 能力注册 / 步数上限 / 打断）                        │
│   公共：event-bus · object-service(文件) · audit · feature-flag               │
├─────────────────────────────────────────────────────────────────────┤
│ ④ AI 服务层（独立部署）                                                        │
│   InferReply(一期) │ ★ RAG Answer │ ★ Agent Plan/Act/Synthesize │ ASR 等   │
│   模型网关：超时 / 降级 / mock|remote                                         │
├─────────────────────────────────────────────────────────────────────┤
│ ⑤ 数据层                                                                      │
│   PostgreSQL（业务库 + 知识库元数据/切片）                                     │
│   ★ Milvus / 兼容向量库（chunk embedding）                                    │
│   Redis（feature flag、SSE replay、通知、指标缓冲）                            │
│   对象存储（原始文档文件）                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

\* `reply`：扩展路由模式（一期话术 / L1 RAG / L2 Agent）。  
\* `admin`：新增知识库管理、关停开关、推理反馈看板。

### 2.2 与一期的关系

| 组件 | 一期 | 二期变更 |
| ---- | ---- | -------- |
| `POST /reply/suggestions/stream` | 单模块 InferReply | 入口不变；服务端按意图分流 |
| `suggestion_event` | 记录候选与采纳 | 扩展 `mode` / `agent_run_id` / 来源标注 |
| AI Gateway | `/v1/reply/stream` 等 | 新增 RAG / Agent 远端契约 |
| 画像 / 订单 / 标签 | 顾问端与后台 CRUD | 对 Agent 开放为 **Capability Tool** |
| 开班信息 | 无独立域 | 本期走知识库「开班计划」静态文档；不接教务实时名额 |

### 2.3 部署视图

- **业务 API**：现有 FastAPI 进程（可水平扩展）；Agent 编排跑在业务进程内（同步编排 + SSE），避免额外运维复杂度。
- **AI 服务**：独立进程/集群；向量检索可与 AI 同机或独立 Milvus。
- **Feature Flag**：`agent_reasoning_enabled` 等写入 Redis + DB 双写；读路径优先 Redis，保证关停秒级生效。
- **文件**：知识库原文件存对象存储（本地可用 MinIO / 本地盘适配）；DB 仅存元数据与 chunk。

## 3. 模块划分

### 3.1 knowledge（知识库）

| 职责 | 说明 |
| ---- | ---- |
| 文档生命周期 | 上传 → 解析切分 → 向量化 → 审核态 → **一键发布生效** |
| 检索 | 按 query 召回 Top-K chunk，返回文本 + 分数 + 文档溯源 |
| 生效版本 | `kb_document.published_version`；检索只读 `status=published` 的 chunk |
| 通知 | 发布成功后写通知事件，侧边栏/推送拉取 |

**四类文档 category：** `group_overview` | `course_plan` | `honor` | `faq`

### 3.2 agent（综合推理）

| 子模块 | 职责 |
| ------ | ---- |
| Intent Router | 判断：一期单模块 / 仅 RAG / 需要 Agent |
| Planner | LLM 输出下一步要调的 capability 列表（受白名单约束） |
| Tool Runtime | 调用五入口；强制 max_steps（默认 3）；超时预算 |
| Synthesizer | 综合证据生成建议 + 来源标注 + 不确定提示 |
| Run Store | 持久化 `agent_run` / `agent_step`，支撑透明展示与反馈 |

### 3.3 五类 Capability（对 AI 的工具声明）

每个 Capability 向 Planner 暴露统一描述：

```text
name / description / input_schema / output_schema / latency_sla
```

| Code | 名称 | 数据来源 | 本期实现 |
| ---- | ---- | -------- | -------- |
| `kb_search` | 知识库检索 | knowledge + 向量库 | 新增 |
| `profile_get` | 客户画像 | `profile` 已确认版本 | 包装既有 service |
| `order_list` | 订单记录 | `order` | 包装既有查询 |
| `tag_list` | 标签分析 | `customer_tag` + `tag` | 包装既有查询 |
| `course_plan_search` | 开班信息 | 知识库 category=`course_plan` | 复用 kb_search 过滤 |

> 日程、实时名额：**不在本期注册表**，开关级禁止调用。

### 3.4 feature-flag（关停）

| Flag Key | 含义 | 关闭后行为 |
| -------- | ---- | ---------- |
| `agent_reasoning_enabled` | 综合推理总开关 | Intent 不再进入 L2；可走 L1 RAG 或一期 InferReply |
| `kb_rag_enabled`（可选） | 知识库 RAG | 关闭则客观事实类也退回一期话术/兜底 |

读写：Admin API 写 DB `sys_feature_flag` + `SET` Redis；业务读 Redis（TTL 短或 pub/sub 失效）。

## 4. 核心流程

### 4.1 侧边栏回复建议（统一入口）

```
顾问触发「生成建议」
        │
        ▼
POST /api/v1/reply/suggestions/stream
        │
        ├─ feature: agent off? ──► 一期 InferReply（简化模式）
        │
        ▼
Intent Router（规则 + 轻量分类）
        │
        ├─ 客观事实查询 ──► L1 RAG Pipeline
        │                      ├─ 检索 score ≥ threshold → 据实生成 + citations
        │                      └─ 否则 → 兜底话术（嵌入顾问姓名）+ 记 blind_spot
        │
        └─ 组合型问题且 agent on ──► L2 Agent Pipeline（SSE 推步骤）
                                   ├─ plan / tool_call / tool_result / synthesize
                                   ├─ steps ≥ max 或预算耗尽 → 强制综合或失败标注
                                   └─ 落库 suggestion_event + agent_run
```

**时延预算（NFR ≤ 5s）：**

| 阶段 | 预算 |
| ---- | ---- |
| Intent + 准备上下文 | ≤ 200ms |
| 单次 Tool 调用 | ≤ 800ms（并行可重叠） |
| LLM plan/synthesize | 合计 ≤ 3.5s |
| 总墙钟 | ≤ 5000ms；超时则降级：已有证据综合 / 或失败标注 |

### 4.2 L1 RAG 详细流

1. 取当前生效知识库版本集合。
2. Embedding(query) → Milvus 检索 Top-K（可按 category 加权）。
3. 过滤 `score < RAG_SCORE_THRESHOLD`。
4. 若无有效 chunk → 兜底模板 + `kb_blind_spot` 日志。
5. 若有 → 调用 AI `RAG Answer`（严格 grounded prompt）→ SSE `suggest_chunk` / `suggest_done`。
6. 写 `suggestion_event.mode=rag`，`candidates_json` 含 `citations`。

### 4.3 L2 Agent 详细流（王芳案例）

1. SSE `agent_step`：`status=planning`。
2. Planner 输出：`profile_get` → `course_plan_search` → `kb_search(faq)`。
3. Runtime 依次/有限并行执行；每步推送 `agent_step`（查了什么、摘要结果、来源）。
4. 顾问若调用 `POST .../agent/runs/{runId}/interrupt`：标记 run=`interrupted`，后续 tool 跳过，进入「按已有证据综合」或等待顾问纠正指令（V1：打断即停止并输出已有结论 + 核实提示）。
5. Synthesizer 输出建议正文 + `sources[]` + `uncertaintyNotes[]`。
6. 顾问确认发送仍走一期 `feedback`（`adopt_and_send_manually`），**系统不代发**。

### 4.4 知识库发布流

```
运营上传文件 → 解析/切分/embedding（异步任务）
    → status=ready_for_review
业务审核（线下流程 + 系统操作人记录）
    → 一键 Publish：切换 published 指针，旧版归档
    → 通知顾问 + audit_log
检索侧只读 published，实现「一键生效」
```

### 4.5 关停回退流

```
超管关闭 agent_reasoning_enabled
  → DB + Redis 立即更新
  → 进行中的 agent_run：协作式取消（下一 step 检查 flag，中止）
  → 新请求：Intent 禁止 L2
验收：关闭后连续 N 次请求 mode ∈ {legacy, rag}，绝不出现 mode=agent
```

## 5. 防幻觉与风控设计

| 层级 | 机制 | 实现要点 |
| ---- | ---- | -------- |
| L1 | 匹配度门槛 | `score < threshold` 不进入生成 |
| L1 | Grounded Prompt | 仅允许使用给定 chunk；禁止外部知识 |
| L1/L2 | 兜底话术 | 模板含 `{advisorName}` |
| L2 | 能力白名单 | Planner 只能选注册表内 tool |
| L2 | 步数上限 | `max_steps=3`（可配置） |
| L2 | 透明 SSE | 每步可见；支持打断 |
| L2 | 不确定标注 | Synthesizer 强制输出 `uncertaintyNotes` |
| 共用 | 顾问确认 | 仅 `feedback` 采纳，无发送 API |
| 共用 | 关停开关 | Redis 秒级 |
| 共用 | 反馈与盲区 | `agent_feedback` / `kb_blind_spot` 反哺 |

## 6. 权限设计

| 角色 | 知识库管理 | 关停开关 | 侧边栏 Agent | 反馈 |
| ---- | ---------- | -------- | ------------ | ---- |
| advisor | 否 | 否 | 是（若开关开） | 是 |
| supervisor | 上传/发布（可按策略） | 否 | 是 | 是 |
| admin / 超管 | 是 | 是 | 是 | 是 |

数据范围：Capability 读画像/订单/标签时，**复用一期 `assert_customer_accessible`**，禁止跨顾问越权。

## 7. 可观测性与指标

沿用一期审计 + 采纳统计，二期增量：

| 指标 | 采集点 |
| ---- | ------ |
| 采纳率 / 修改率 | `suggestion_event.action`（按 `mode` 分组） |
| 兜底率 | `mode=rag` 且 `fallback=true` |
| 推理失败率 | `agent_run.status=failed|insufficient` |
| 任务完成时间 | `suggest 开始` → `feedback.acted_at`；另记 `agent_run.latency_ms` |
| Agent 耗时 | `agent_run.latency_ms`；告警阈值 5000ms |

Redis Stream 主题建议：

- `stream:kb:published`
- `stream:agent:run_finished`
- `stream:adoption:recorded`（一期已有，payload 增 `mode`）

## 8. 技术选型（二期增量）

| 领域 | 选型 | 说明 |
| ---- | ---- | ---- |
| 业务 API | FastAPI（现有） | knowledge / agent 以 service 模块落地 |
| 向量库 | Milvus（与 HLD v2.6 一致） | 开发可用内存/轻量替代，接口层抽象 `VectorStore` |
| Embedding | AI 服务侧模型 | 经 AI Gateway，业务不直连模型厂商 |
| 异步任务 | 进程内 asyncio 队列 + DB 任务表；或 Redis 消费 | 文档解析/向量化 |
| 配置开关 | PostgreSQL + Redis | 双写，读 Redis |

## 10. 风险与演进

| 风险 | 缓解 |
| ---- | ---- |
| 向量检索召回差导致兜底率高 | 盲区日志驱动补文档；调 threshold / 切分策略 |
| Agent 规划跑偏 | 白名单 + max_steps + 透明打断 |
| 画像脏数据 | 来源时效展示；人审发送 |
| Milvus 运维成本 | `VectorStore` 抽象；本地可降级 pgvector（可选） |

**后续二期+：** `schedule_query`、`seat_realtime` 注册为新 Capability，不改主链路。
